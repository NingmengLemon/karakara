# 记录：曲库扫描与元数据过滤的证据（2026-09-12）

> 这是**一次实测的记录**，不是规范。开关的现状与默认值写在
> [../current/metadata-filter.md](../current/metadata-filter.md)。
> 重新扫描曲库时请按本文的口径量，别凭感觉调配置。

## 度量规模

真实曲库 **6622 个 `.lrc` / 556,730 个非空行**。关键度量走的是**真实解析路径**
（`Lyrics.loads` 之后的行文本），不是裸文件文本。这一点很重要：解析器会先消费掉一些东西
（见下面 `id3_tags` 那条）。

## 关键字扩到约 200 项

| | 命中行数 |
|---|---|
| 旧配置 | 11,586 |
| 新配置 | 12,735 |
| 丢失 | **0** |
| 新增 | 1,149 |

新增项里 **45% 位于文件中段**，最常见的是 `music...`(94)、`♪`(73)、`...`(69)、`終わり`(52)、
`-END-`(37)、`undefined`(19)，没有一条像歌词。这些行此前会被真的送去对齐，既浪费请求，
也可能产出无意义的词级时间。

## 各开关的判据

- **`pure_numbers` 保持关闭。** 纯数字行里混着演唱内容：`1`/`2`/`3`（「コンコンきつね」的
  报数演唱）、`1234`、`11111111111111111111111111111111`（「魔理沙は大変なものを盗んで
  いきました」的连打）。77 行里至少 5 个文件的纯数字行是歌词。
- **`parenthetical` 必须是白名单 + 整行匹配**，不能做成形状规则：把「整行被括号包裹」当规则
  用会命中 **10,163 行 / 1,887 文件**，其中 49.7% 在文件中段，绝大多数是歌词本身
  （`（与你同在）`、`(By your side)`、`「よっしゃー行くぞ」`）。改成白名单 markers 之后是
  **37 行 / 15 文件**，逐条核对全是真段落标记。
- **`id3_tags` 打开后在本管线里是空转的**：`[ti:] [ar:] [by:] [offset:]` 这类标签会被
  `lemony-lrc-parser` 先收进 `lyrics.metadata`，不会以「行」的形态到达过滤器。裸文本里有
  **495 行**这种标签，到达过滤器的 **0 行**。保留开关只是为了让 `MetadataFilter` 独立使用时
  仍然正确，不要指望它带来召回提升。（早期一次统计曾把这 495 行算成收益，那是按裸文本数的。）

## 假阳性：这套过滤最严重的失败模式

删掉一行就等于丢掉一句歌词。以下形态连同真实命中证据一起固化在 `tests/test_metadata.py`：

| 不能命中的形态 | 为什么 |
|---|---|
| `合：赔盏茶才算周到` | 对唱/角色分句标记，**冒号后就是歌词正文**（`合` 48 行、`洛` 28、`雏` 27、`绫` 15…） |
| `8:07に君を待ってる` / `8:00 二号车二节…` | 「时间 + 歌词」 |
| `_(:з」∠)_` | 颜文字 |
| `By the way, do you like baseball?` / `Bye for now` | 英文歌词里以 By 开头 |
| `谢谢 想说谢谢你` / `谢谢，我吃饱了` | 「谢谢」开头的歌词（只有 `特别感谢`/`鸣谢` 这类强限定词才算署名） |
| `Thanks for the meal` | 英文歌词（只保留 `special thanks`/`produced by` 这类） |
| `**你是什么垃圾？**` / `****ed get right now` | 装饰符号开头的歌词 |
| `（与你同在）` / `(By your side)` | 整行括号包裹的歌词（10,163 行 / 1,887 文件） |
| `1` / `3` / `1234` / `1111…` | 报数与连打演唱 |

**明知而保留的风险**：自定义模式「X by Y」是形状规则，英文歌词 `Sound by the sea` 这类会被
判成署名（本库实测 0 例）；单字关键字（`词`/`曲`/`歌`/`唱`/`译`/`绘`/`调`/`混`）形态上仍要求
「整行以它开头并紧接冒号」，实测 0 误伤，但信息量低，遇到误伤优先砍它们。

## 为什么不预先 pop 掉元数据行

`_line_sample_range` 在行没有 `end` 时一律取下一行的时间戳，并不看那一行是不是元数据，
所以元数据行**仍然在充当切段边界**。看起来「应该先把它们摘掉」，实测相反：

- 摘掉会让 **219/4971** 个文件里的 **261** 个切段发生变化，其中 **250 个是变长**：
  `[上一行, 署名行]` 变成 `[上一行, 下一行歌词]`，把器乐段也圈了进去。
- 也就是说：**留着署名行反而让切段更紧**，送给对齐器的片段里混进的伴奏更少。
- 位置分布也支持这个决定：当前规则命中的元数据行 **78.7% 在前 3 行**、只有 0.8% 在中段，
  绝大多数本来就落在首尾，不会破坏歌词行的切段。
- 真正需要 pop 的情形（署名行被塞在中段形成错误边界）在本库里没有观察到。

## 重新扫描时的注意事项

1. 逐文件 `Lyrics.loads`，统计「行文本跨文件重复度」：元数据行（尤其 `XX : YYY` 形式）
   高度重复，歌词行几乎唯一。这是最强的信号。
2. 对每个候选采集：命中文件数、命中行数、长度分布、是否含假名或汉字、是否位于文件中段、
   值的多样性。
3. 做**假阳性检查**：命中的行里有多少像歌词。别用单一启发式下结论（「长度 > 24 或含 ≥4 个
   假名」这种规则会把 `大提琴 : Geri Sutyak` 这类真署名也标成可疑），要逐条看样例。
4. 写进配置后，用「旧配置命中 → 新配置命中」的差集验证**丢失为 0**，并抽样核对新增项。

两个写配置时的技术坑：

- **不要写裸 `(?i)`**：所有分支会被 `|` 拼成一条正则，裸 `(?i)` 不在表达式开头，
  `re.compile` 会抛 `global flags not at the start of the expression`。要用 `(?i:...)`。
- **TOML 里 `\s` 要用单引号字面量字符串**（或写 `\\s`），双引号会报 `Unescaped '\' in a string`。
