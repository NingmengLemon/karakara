# 记录：把行尾裁到「人声结束」的可行性（2026-09-23）

> 这是**一次实测的记录**，不是规范。现状行为写在
> [../current/aligner.md](../current/aligner.md) 与 [../current/limits.md](../current/limits.md)。
> 本文回答一个问题：**能不能在检测到人声活动结束后提前结束当前行**，因为一行唱完之后
> 剩下的内容常常全是间奏。

## 问题是怎么来的

送给对齐器的片段是 ``[本行起点, 下一行起点)``（``core._line_sample_range``）。如果一行唱完
就没人声了，这段窗口的后半截全是间奏。而对齐器 HubertFA 的输出是**对整段的连续划分**
（静音与呼吸也占区间），于是最后一个单元会把剩下的时间吃掉。产物里的行尾正是「最后一个
单元的结束时刻」（``core._align_line`` 里的 ``line.end``），所以这段间奏会直接变成
「这一行的高亮一直拖到间奏结束」。

## 方法

- **样本**：8 首歌（5 日文 / 2 英文 / 1 中文），从 `D:\MUSIC` 只读取用，共 **351 行**有效窗口。
- **人声**：`UVR_Demucs_Model_1` 现跑一次并缓存到 `tmp/line_tail/vocals/`。
- **判据**：把分离人声压成 20ms 一窗的 RMS 曲线（归一化到全曲峰值 1.0），取「最后一次
  持续 ≥200ms 超过阈值」的位置当人声结束点；主口径阈值 **0.05**，另跑 0.02/0.10/0.20 看敏感性。
- **三段测量**：A 普遍程度（逐行落盘 `tmp/line_tail/<歌名>.json`）；B 对照实验
  （长尾行 vs 无尾行，各跑完整窗口与裁剪窗口两次对齐）；C 全量扫描（每行都跑一次完整窗口
  对齐，把「产物行尾」与「人声结束」对起来）。

## 结论 1：尾部间奏确实常见，但集中在少数行

| 指标 | 数值 |
|---|---|
| 行窗口里尾部无人声段的中位 / 均值 / p90 / 最大 | 0ms / 788ms / 450ms / **88.58s** |
| 尾部 > 500ms 的行 | 33/351（9.4%） |
| 尾部 > 1s 的行 | 22/351（6.3%） |
| 尾部 > 5s 的行 | 13/351（3.7%） |
| 尾部无人声段合计 | 277s，占全部行窗口 1583s 的 **17.5%** |

也就是说：**中位数行没有尾巴，但少数行带着很长的尾巴**；按音频时长算，送进对齐器的音频有
六分之一是尾部间奏。

阈值敏感性很温和（同一批行，只换阈值）：

| 阈值 | tail 中位 | tail > 2s 的比例 | 整段无人声的行 |
|---|---|---|---|
| 0.02 | 0ms | 4.2% | 2 |
| 0.05（主口径） | 0ms | 5.1% | 2 |
| 0.10 | 0ms | 5.7% | 3 |
| 0.20 | 80ms | 6.5% | 3 |

## 结论 2：产物层面的缺陷率是 1.5%，但最严重的能到 88 秒

把「产物的行尾」减去「人声真正结束的时刻」（overshoot），333 行里：

| overshoot | 行数 |
|---|---|
| 中位 / 均值 / p90 | **−10ms** / 267ms / 80ms |
| > 500ms | 7（2.1%） |
| > 1s | 5（**1.5%**） |
| > 2s | 3（0.9%） |
| > 5s | 2（0.6%） |
| 最大 | **88.58s** |

**绝大多数行的行尾是准的**（中位 −10ms，即行尾略早于人声结束），所以这不是一个普遍缺陷，
而是少数行的严重缺陷。最严重的几例：

| 歌 | 行 | 窗口 | 人声结束 | 产物行尾 | 晚 |
|---|---|---|---|---|---|
| STARSET - Carnivore | 46（最后一行） | 95340ms | 6760ms | 95340ms | **88580ms** |
| Rick Astley | 72（最后一行） | 10593ms | 5220ms | 10593ms | 5373ms |
| YOASOBI - 夜に駆ける | 26 | 5180ms | 2000ms | 5180ms | 3180ms |
| YOASOBI - 夜に駆ける | 14 | 2030ms | 860ms | 2029ms | 1169ms |
| ReoNa - SACRA | 4 | 9270ms | 8240ms | 9270ms | 1030ms |

**缺陷高度集中在最后一行**：最后一行 **2/7（28.6%）**命中，其余行只有 3/326（0.9%），
相差约 30 倍。原因是最后一行没有下一行，``_line_sample_range`` 取**音频末尾**当窗口右端，
于是整段尾奏都进了片段。

## 结论 3：裁剪对对齐结果的影响很小，而且正好修掉拉伸

对照实验：**实验组** 22 行（尾部 > 1s）、**对照组** 22 行（尾部 < 200ms），每行都跑两次
（完整窗口 / 裁到「人声结束 + 500ms」）：

| | 实验组（22 行） | 对照组（22 行） |
|---|---|---|
| 返回的单元文本完全一致 | 22/22 | 22/22 |
| 连边界都完全一致 | 1/22 | **22/22** |
| 最大边界差：中位 / p90 / 最大 | 175ms / 2530ms / 183412ms | 0ms / 0ms / 0ms |
| 末单元结束时刻的变化（裁剪减完整） | 中位 −9ms，p10 −2680ms，最小 −88080ms | 0ms |

两件事因此成立：

1. **裁剪不会改变「认出了哪些字」**（22/22 文本一致），对照组更是连边界都不动，说明这个
   实验本身没有引入噪声。
2. **裁剪恰好修掉拉伸**：末单元被拉长的行，裁剪后回到人声结束附近；对照组没有一行被拉长。

## 结论 4：「误切」的 5 例里有 4 例其实是拉伸，1 例是真漏检

A/B 里「裁剪点早于完整对齐的末单元结束」的有 5 行。逐条用同一份能量曲线判读被裁掉那段的
活跃度（阈值 0.05）：

| 行 | 被裁段活跃度 | 判读 |
|---|---|---|
| ReoNa - SACRA line 4 | 0.0362 | 拉伸（被裁段无人声） |
| Rick Astley line 72 | 0.0147 | 拉伸 |
| STARSET line 46 | 0.0030 | 拉伸 |
| YOASOBI line 26 | 0.0017 | 拉伸 |
| YOASOBI line 14 | **0.2045** | **真漏检**：被裁段确实有人在唱 |

前 4 例的共同特征是「完整窗口的末单元恰好结束在窗口末尾」，也就是连续划分式对齐器把
尾部静音摊给了最后一个单元，裁剪只是把这个摊派去掉。第 5 例是判据本身的失败：该行窗口
2030ms、判据说人声在 860ms 结束，但 1360ms 之后仍有明显能量（0.2045），多半是「安静一段
之后又有一小段唱词」而那段短于 200ms 的持续门槛。

**所以判据的失败率在这一批里是 1/22（4.5%），失败模式是「漏掉安静间隙之后的短促人声」。**

## 结论 5：一个没有判别力的判据（记下来免得重犯）

一开始我用的指标是「末单元是否贴到窗口末尾」，全量扫描给出 **246/335（73.4%）**。这个数字
看着很吓人，其实**没有判别力**：绝大多数行的窗口末尾本来就等于人声结束（下一行紧接着就唱），
贴到段尾是正常行为。有判别力的是「产物行尾减去人声结束」（结论 2 的 overshoot），它给出
1.5%。**指标要对着「错在哪」设计，而不是对着「看起来像什么」设计。**

## 建议（尚未实现）

可行，但**收益集中、风险真实**，建议按下面的形态做，并且先做成开关而不是改默认：

- **触发条件**：尾部无人声段 > **1s**（更短的尾巴裁了没意义，见结论 3 的对照组）。
- **判据**：20ms 窗 RMS 曲线，阈值 **0.05**（相对全曲峰值），持续 **≥200ms**。
- **余量**：裁剪点取「人声结束 + **500ms**」，给混响尾巴、呼吸和对齐器留上下文。
- **守卫（关键）**：裁剪前再查一次**裁剪点之后到窗口末尾**的平均活跃度，**≥0.05 就不裁**。
  这条守卫在本文的样本上会拒绝唯一的真漏检（0.2045），而放过 4 例确认的拉伸（0.0017 到
  0.0362）。
- **实现位置**：`core._line_sample_range` 的右端（能量曲线在 `gen_kara` 里已经建好，不需要
  额外解码），逐行 debug 日志 + 每首歌汇总裁了几行。
- **预期效果**（按本文样本外推）：改变约 **1.5%** 行的产物（修掉拉伸，最大一例 88s）；
  送进对齐器的音频减少约 **17.5%**；单元文本不变。
- **特别值得单独修的一条**：最后一行的窗口右端是**音频末尾**，它的命中率是其余行的 30 倍。
  即使不做整体裁剪，也应该给最后一行一个上限。

## 复现

```powershell
# B 阶段：对照实验（需要对齐服务）
uv run --script scripts/hubertfa_aligner_server.py --preload --port 18120

# C 阶段：误切判读、全量扫描、缺陷率

```

原始数据在 `tmp/line_tail/`（gitignored）：逐行统计、A/B 结果、全量扫描、缺陷表各自一个
JSON，判定都可以从它们重算。

## 没做的部分

- **没有人工听感确认**：结论 4 的判读靠能量曲线，第 5 例（0.2045）应当有人听一遍确认它
  是不是真在被裁掉的那段里唱。
- **样本只有 8 首**：1.5% 这个缺陷率的分母是 333 行，落在 5 行上，置信区间很宽。
- **没有验证「裁剪后产物整体更好」**：本文只证明了单元文本不变、拉伸被修掉、被裁段多为
  静音；「更好」的最终判据仍是有真值的人工标注（BER/IOU）。
