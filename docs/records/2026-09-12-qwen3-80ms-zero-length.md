# 记录：qwen3 后端的 80ms 量化与零长度词（2026-09-12）

> 这是**一次实测的记录**，不是规范。它回答的问题是「qwen3 后端的精度上限锁在哪，
> 以及能不能绕过去」。现状行为写在 [../current/aligner.md](../current/aligner.md)。

## 结论先说

零长度词不是本仓库的 bug，而是 qwen3 后端**离散时间槽**设计的必然结果：模型把时间轴
切成 80ms 的格子，真实时长短于一个格子的单元就会拿到 `start == end`。改配置、改调用
粒度都绕不过去，只能换后端（已换成 HubertFA）。

## 根因（源码级，不是猜的）

- 模型 config 里 `timestamp_segment_time = 80`，时间戳来自**离散 token**
  （`timestamp_ms = token_id * 80`），所以每个单元边界都被量化到 80ms 的格子上。
- `parse_timestamp` 把相邻两个边界 token 配成一个单元的 `(start, end)`。
- 库自带的 `fix_timestamp` 只用最长递增子序列修**递减**的异常，判据是
  `data[j] <= data[i]`，**允许相等**，所以零长度单元会被原样留下。

## 实测规模

6 首歌、1497 个单元的真实运行日志，合计 337 个零长度（**22.5%**）：

| 歌 | 单元数 | 零长度 | 占比 | 时间戳栅格 |
|---|---|---|---|---|
| Saya - 失う | 252 | 27 | 10.7% | 80ms |
| ReoNa - SACRA | 222 | 34 | 15.3% | 20ms（被 `fix_timestamp` 插值过） |
| Cryu - 蒲公英 | 141 | 59 | **41.8%** | 80ms |
| `samples/` 三首 | 882 | 217 | 24.6% | — |
| **合计** | **1497** | **337** | **22.5%** | |

位置与上下文：**70% 落在行中**（不是行首或行末），**80% 紧跟前一个单元的结束时刻**，
也就是「被前一个单元吞掉」。所有单元跨度都是 80ms 的整数倍
（0/80/160/240/320/400/480/560/640/800/880/960…）。

## 试过、走不通的路

粒度由 qwen-asr 内部分词器决定，外部只能通过 `language` 间接选择：

| `language` | 分词器 | 单元 |
|---|---|---|
| Japanese | `tokenize_japanese` → nagisa 形态素 | 词（`君`/`が`/`好き`/`だ`/`から`） |
| Korean | `tokenize_korean` → soynlp | 词 |
| 其他（含 Chinese/English） | `tokenize_space_lang` → `split_segment_with_chinese` | 汉字逐字，非汉字连续段合成一个 token |

- 日文歌的单元是 nagisa 的**词**，比字粗：一个词整体不足 80ms 就整块塌掉，这正是日文歌
  零长度率最高的原因（蒲公英 41.8%）。
- **「逐字插空格」绕不过去**：实测 `"君が好きだから"` 与 `"君 が 好 き だ か ら"` 返回
  **完全相同**的 5 个单元与时间戳，nagisa 照样把空格重新切成同样的词。
- **改成 `language="Chinese"` 更糟**：日文假名不算 `is_cjk_char`，`君が好きだから` 会被切成
  `["君", "が好きだから"]`，比 nagisa 还粗。
- 真要走「更细的单元 + 再聚合回词」，得给上游 `encode_timestamp` 加显式粒度开关，属于另一件事。

`align()` 里 `language` **只**用于分词，模型的音频输入与它无关，所以以上都是死路。

## 换成 HubertFA 之后（对照）

同样的输入换成默认后端 `hfa`，日文同一首歌上：

| | qwen3 | HubertFA |
|---|---|---|
| 零长度单元 | 59 / 141（41.8%） | 5 / 260（**1.9%**） |
| 最小非零跨度 | 80ms | **6.8ms** |
| 行区间覆盖率 | 46.1% | **88.8%** |

注意「零长度率」在两个后端之间**不可直接比**：HubertFA 的输出是对整段的连续划分
（静音与呼吸也占区间），结构上就产生不了零长度单元。有信息量的是覆盖率与最小非零跨度。

## 合并前后（产物规范化）

序列化按 `[start]文本[end]` 写标签，零长度单元会写出与前一个完全相同的第二个标签；
解析器把这种重复标签当异常丢掉（自带 `Unordered time tag dropped`）。同一首歌：

| 产物 | 时间标签数 | 连续重复标签 | 解析器告警 | 字符多重集与输入一致 |
|---|---|---|---|---|
| 处理前 | 234 | **67** | **62** | 是 |
| 仅合并（默认行为） | 159 | **0** | **0** | 是 |
| 合并 + 细分 | 195 | **0** | **0** | 是 |

同一首歌上 `--refine-collapsed-words` 把 60 个零长度里的 38 个（63%）摊进了后面的空隙，
其余（后面紧跟一个同刻开始的正常单元、没有空隙）保持合并。
