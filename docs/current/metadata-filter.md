# 元数据行滤除

元数据行是**不是歌词、但长得像一行歌词**的东西：作词/作曲/编曲/演唱/混音/母带/曲绘/PV/翻译/
出品这类制作人员与鸣谢信息，以及段落标记（`(间奏)`、`【サビ】`、`---`、`Music:`、`End`、
`終わり`）。它们不该被送去对齐。

配置在 `metadata_filter.toml`，实现是 `karakara/utils/metadata.py`，用 `--metadata-filter`
可以换成别的文件（默认按项目根目录定位，不依赖 CWD）。

## 五种检测策略（逻辑或）

| 开关 | 形态 | 默认 |
|---|---|---|
| `keywords` | 整行以关键字开头并紧接冒号（`^\s*(?:kw)\s*[：:].*`，`IGNORECASE`） | 开，约 200 项 |
| `id3_tags` | `[ti:...]` / `[by:...]` 这类标签 | 开，但**在本管线里是空转的**（见下） |
| `parenthetical` | 整行是括号包裹的段落标记，全角半角都认 | 开 |
| `pure_numbers` | 整行只有数字 | **刻意关闭** |
| `custom` | 自定义正则 | 7 条 |

两条容易踩的认知：

- **`id3_tags` 开着但不产生效果**：`[ti:] [ar:] [by:] [offset:]` 这类标签会被
  `lemony-lrc-parser` 先收进 `lyrics.metadata`，不会以「行」的形态到达过滤器。保留开关只是
  为了让 `MetadataFilter` 独立使用时仍然正确。
- **`parenthetical` 必须是白名单加整行匹配**，不能做成「整行被括号包裹」这种形状规则：
  那样会命中大量歌词本身（`（与你同在）`、`(By your side)`）。

## 最重要的失败模式：假阳性

**删掉一行就等于丢掉一句歌词**，所以这套过滤是宁可漏、不可误伤。「绝对不能命中」的形态连同
真实命中证据一起固化在 `tests/test_metadata.py`：对唱分句标记（`合：赔盏茶才算周到`）、
「时间 + 歌词」（`8:07に君を待ってる`）、颜文字、以 By 或 Thanks 开头的英文歌词、以「谢谢」
开头的歌词、装饰符号开头的歌词、整行括号包裹的歌词、报数与连打演唱（`1`/`1234`）。

**明知而保留的风险**：`custom` 里有一条「X by Y」形状规则，英文歌词 `Sound by the sea`
这类会被判成署名（本库实测 0 例，真遇到就删掉那条）；单字关键字（`词`/`曲`/`歌`/`唱`/`译`/
`绘`/`调`/`混`）形态上仍要求「整行以它开头并紧接冒号」，实测 0 误伤。

## 元数据行仍然充当切段边界（刻意的）

`core._line_sample_range` 在一行没有 `end` 时一律取下一行的时间戳，并不看那一行是不是元数据，
所以元数据行**仍然在当切段边界**。看起来「应该先把它们摘掉」，测量结果相反：摘掉会让一批
文件的切段变长，把器乐段圈进送给对齐器的片段。实测数据见
[records/2026-09-12-metadata-corpus-scan.md](../records/2026-09-12-metadata-corpus-scan.md)。

## 改配置之前先量

配置里每条都注明了命中规模与假阳性风险，改动时请用同一套度量重跑一遍：以「行文本跨文件
重复度」找候选（元数据行高度重复，歌词行几乎唯一），逐条看样例做假阳性检查，写进配置后用
「旧配置命中减新配置命中」的差集验证**丢失为 0**。完整口径与两个 TOML/正则的技术坑见
[records/2026-09-12-metadata-corpus-scan.md](../records/2026-09-12-metadata-corpus-scan.md)。
