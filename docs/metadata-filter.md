# 元数据行滤除

配置文件 `metadata_filter.toml`，实现 `src/karakara/utils/metadata.py`，用 `--metadata-filter` 可以换成别的文件（默认按项目根目录定位，不依赖 CWD）。

元数据行指：作词/作曲/编曲/演唱/混音/母带/曲绘/PV/翻译/出品 等**制作人员与鸣谢信息**，以及**段落标记/注释**（`(间奏)`、`【サビ】`、`---`、`Music:`、`End`、`終わり`）。它们不是歌词，不应该被送去对齐。

## 检测策略（逻辑或）

| 开关 | 形态 | 现状 |
|---|---|---|
| `keywords` | 整行以关键字开头并紧接冒号（`^\s*(?:kw)\s*[：:].*`，`IGNORECASE`） | 开，约 200 项 |
| `id3_tags` | `[ti:...]` / `[by:...]` 等 | 开，但**在本管线里是空转的**（见下） |
| `parenthetical` | 整行是括号包裹的段落标记，全角/半角都认 | 开 |
| `pure_numbers` | 整行只有数字 | **刻意关闭**（见下） |
| `custom` | 自定义正则 | 7 条 |

## 为什么这些开关是这么定的（都有实测证据）

度量规模来自对真实曲库 6622 个 `.lrc` / 556,730 个非空行的统计；**关键度量走的是真实解析路径**（`Lyrics.loads` 之后的行文本），而不是裸文件文本——这一点很重要，因为解析器会先消费掉一些东西（见 `id3_tags`）。

- 关键字补到约 200 项后：旧配置命中 **11,586 行** → 新配置 **12,735 行**，**丢失 0 行**，新增 1,149 行；新增项中 **45% 位于文件中段**，最常见的是 `music...`(94)、`♪`(73)、`...`(69)、`終わり`(52)、`-END-`(37)、`undefined`(19)——没有一条像歌词。**这些行此前会被真的送去对齐**，既浪费请求，也可能产出无意义的词级时间。
- `pure_numbers` **保持关闭**：纯数字行里混着演唱内容——`1`/`2`/`3`（「コンコンきつね」的报数演唱）、`1234`、`11111111111111111111111111111111`（「魔理沙は大変なものを盗んでいきました」的连打）。77 行里至少 5 个文件的纯数字行是歌词。
- `parenthetical` **必须是白名单 + 整行匹配**，不能做成形状规则：把「整行被括号包裹」当规则用会命中 **10,163 行 / 1,887 文件**，其中 49.7% 在文件中段，绝大多数是歌词本身（`（与你同在）`、`(By your side)`、`「よっしゃー行くぞ」`）。扩展 markers 之后是 **37 行 / 15 文件**，逐条核对全是真段落标记。
- **`id3_tags` 打开后在本管线里是空转的**：`[ti:] [ar:] [by:] [offset:]` 这类标签会被 `lemony-lrc-parser` 先收进 `lyrics.metadata`，不会以「行」的形态到达过滤器——裸文本里有 **495 行**这种标签，到达过滤器的 **0 行**。保留开关只是为了 `MetadataFilter` 独立使用时仍然正确，不要指望它带来召回提升。

## 假阳性是这套过滤最严重的失败模式

删掉一行就等于丢掉一句歌词，所以「绝对不能命中」的形态连同真实命中证据一起固化在 `tests/test_metadata.py` 里：

| 不能命中的形态 | 为什么 |
|---|---|
| `合：赔盏茶才算周到` | 对唱/角色分句标记，**冒号后就是歌词正文**（`合` 48 行、`洛` 28、`雏` 27、`绫` 15…） |
| `8:07に君を待ってる` / `8:00 二号车二节…` | 「时间 + 歌词」 |
| `_(:з」∠)_` | 颜文字 |
| `By the way, do you like baseball?` / `Bye for now` | 英文歌词里以 By 开头 |
| `谢谢 想说谢谢你` / `谢谢，我吃饱了` | 「谢谢」开头的歌词（只有 `特别感谢`/`鸣谢` 这类强限定词才算署名） |
| `Thanks for the meal` | 英文歌词（只保留 `special thanks`/`produced by` 这类） |
| `**你是什么垃圾？**` / `****ed get right now` | 装饰符号开头的歌词 |
| `（与你同在）` / `(By your side)` | 整行括号包裹的歌词（10,163 行 / 1,887 文件） |
| `1` / `3` / `1234` / `1111…` | 报数与连打演唱 |

**残留风险（明知而保留）**：自定义模式 ②「X by Y」是形状规则，英文歌词 `Sound by the sea` 这类会被判成署名。本库实测 0 例；真遇到就在 `[custom] patterns` 里删掉那一条。单字关键字（`词`/`曲`/`歌`/`唱`/`译`/`绘`/`调`/`混`）在形态上仍要求「整行以它开头并紧接冒号」，实测 0 误伤，但单字信息量低，如果别的语料误伤就优先砍这几个。

## 刻意**不**做的事：处理前把元数据行整体 pop 掉

`_line_sample_range` 在行没有 `end` 时一律取下一行的时间戳，并不看那一行是不是元数据，所以元数据行**仍然在充当切段边界**。看起来"应该把她们先摘掉"，但实测相反：

- 摘掉元数据行会让 **219/4971** 个文件里的 **261** 个切段发生变化，其中 **250 个是变长**——`[上一行, 署名行]` 变成 `[上一行, 下一行歌词]`，把器乐段也圈了进去。
- 也就是说：**留着署名行反而让切段更紧**，送给对齐器的片段里混进的伴奏更少。
- 真正需要 pop 的情形（署名行被塞在中段、形成错误边界）在本库里没有观察到。
- 位置分布也支持这个决定：当前规则命中的元数据行 **78.7% 在前 3 行**、只有 0.8% 在中段——也就是说元数据行绝大多数本来就落在"首尾"，不会破坏任何歌词行的切段。

## 重新扫描曲库（改配置之前请先量）

配置里每条都注明了命中规模与风险，改动时请用同一套度量重跑一遍。可用的思路（脚本可以放在 `tmp/` 下，注意**只读**曲库）：

1. 逐文件 `Lyrics.loads`，统计「行文本跨文件重复度」——元数据行（尤其 `XX : YYY` 形式）高度重复，歌词行几乎唯一。这是最强的信号。
2. 对每个候选采集：命中文件数、命中行数、长度分布、是否含假名/汉字、是否位于文件中段、值的多样性。
3. 对每个候选做**假阳性检查**：命中的行里有多少像歌词。别用单一启发式下结论（「长度>24 或含≥4 个假名」这种规则会把 `大提琴 : Geri Sutyak` 这类真署名也标成可疑），要逐条看样例。
4. 写进配置后，用「旧配置命中 → 新配置命中」的差集验证 **丢失为 0**，并把新增项抽样核对。

两个写配置时的技术坑：

- **不要写裸 `(?i)`**：所有分支会被 `|` 拼成一条正则，裸 `(?i)` 不在表达式开头，`re.compile` 会抛 `global flags not at the start of the expression`。要用作用域写法 `(?i:...)`。
- **TOML 里 `\s` 要用单引号字面量字符串**（或写 `\\s`），双引号会报 `Unescaped '\' in a string`。
